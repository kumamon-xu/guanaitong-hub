# 应用内扣卡兑换

v0.7.0 将结算和确认放在本地应用内。登录仍使用每卡独立官网会话；确认提交后调用官网交易接口，不自动操作官网购物车或点击网页提交按钮。

## 使用流程

1. 在商品详情选择来源卡片，点击「应用内结算」；也可在兑换清单按卡点击「结算并兑换」。
2. 选择实时 SKU、数量与该卡官网已有地址。组合商品需选择对应子规格。
3. 获取结算预览，核对兑换额、商品件数、运费、地址和本卡额度。`total_amount` 为兑换额，`total_pieces` 为件数；`is_need_verify` 的 1 表示要求验证，2 表示不要求验证。
4. 阅读商品协议并明确确认使用此卡兑换。只有有效且已确认的预览可提交；最终确认会产生真实订单和扣卡。
5. 在回执或订单页查看应用内兑换记录。结果待核对时查询订单状态，不重新点击同一请求。原清单保留，核对后自行移除已兑换商品。

## 数据与一致性

- 商品码、库存池和 SKU 必须属于选定卡的具体来源；数量、库存、配送及结算明细重新读取，价格不取自页面输入或旧缓存。
- 预览有效期为两分钟。提交前重做结算并校验摘要，价格、地址、协议或余额变化时拒绝沿用旧确认。
- 最终写入只有固定的 `exchangeOrder/exchange` 路径，不加入只读重试链。发出请求前先持久化加密记录；网络超时、连接中断或结果缺失均保留待核对状态，不自动重发。
- 多商家订单需要核对全部返回的商家状态，区分兑换成功、待确认、全部关闭和部分完成。
- 未解决记录优先展示并始终保留，已结束记录只显示最近 100 条。其他卡的交易历史不会挤掉需要解除保护的旧记录。
- 提交中的记录在重启后标为结果未知。v4 备份包含兑换记录；恢复旧备份不会删除当前数据库已有的不确定订单。
- 同一交易的后续备份可以补齐缺少的订单号或商家订单号，即使本地恢复时间晚于备份时间。补齐后仍需查询官网确认，不能只凭备份中的成功状态解除保护；不同卡片、交易内容或订单号冲突时恢复失败并保留原数据。
- 未取得确定订单号时，订单列表为空也不能证明写入失败。该卡会保留保护状态，避免自动产生重复扣款。

## 当前交易范围

覆盖已解析的普通实物 SKU 与已知组合商品结构，使用本卡普通官网地址。额外短信验证、充值专用字段、自提门店、企业固定配送、周期商品、未知规格结构或外部收银台不按普通扣卡流程继续。程序不会代填验证码、额外支付或猜测必填交易参数。

接口兼容依赖官网实际返回结构，HTTP 成功不代表业务或扣卡成功。最终提交只使用模拟服务端验收，真实卡在本轮仅验证到结算预览。

## 测试入口

`npm run test:desktop` 包含两种隔离测试：预览模式禁止最终提交；完整模式仅使用虚构卡片和模拟接口，验证一次提交与回执查询，真实网络请求为零。

`npm run test:trade-preview` 是独立的真实卡预览测试。凭据通过不回显的标准输入和一次性本机通道传递，不写入源码、参数或环境变量。它只接受卡号与密码，没有最终提交模式。

- 后端强制 `HUB_TRADE_PREVIEW_ONLY=1`，最终提交按钮禁用。
- 网络层另行拦截最终兑换以及未允许的写入。
- 只读打开原数据库，在临时隔离目录中运行新程序；不会升级原有用户数据库。
- 测试不调用 `submitOrder`，停在结算预览并核对余额未变化。报告和截图留在被 Git 忽略的 `.private/trade-preview/`。
